# S2 — Importer + reconciliation

_Rewritten by the planning hub after S1 (S1's STATUS says "S2.md not yet written" — an earlier draft existed; this
version replaces it and is based on S1's real schema and on a real nightly backup)._

## Goal

Build `packages/import`: a tool that loads a legacy `farooq-co-erp-backup` JSON file into the S1 Postgres schema as a
proper double-entry ledger, then proves the new ledger reproduces the old app's shop and supplier balances **to the
paisa**. This is the "will the migration be 100%?" safety net (`CLAUDE.md` rule 8). No Payments logic yet (S3), no UI (S4).

**Prerequisite:** S1 done (it is: `docs/STATUS.md`, CI green). Run `pnpm install && pnpm test` first and confirm green
before changing anything.

## Why the real backup alone proves little — read this

With 12 invoices, 7 payments, 0 returns and 0 opening balances, "0 differences on the real backup" would pass even if
returns, opening balances, reversals, drafts and cancellations were all broken. So S2 has **two** proofs, and STATUS must
say plainly which is which:
1. the real backup (real data, thin coverage), and
2. a **rich synthetic fixture** that exercises every branch of the legacy Ledger (see §6). This is the one that actually
   validates the logic.

## Scope

### 0. Extract the DB layer into `packages/db` (`@farooq/db`) — do this first, as its own commit

`packages/import` and `apps/api` both need the schema, migrations, client and the embedded-postgres test helper. Move
`apps/api/src/db/{schema,client,env,migrate,dev-db}.ts`, the `migrations/` folder and the embedded-postgres global-setup helper
into `packages/db`; make `apps/api` depend on it. Purely mechanical: the existing 15 tests must still pass unchanged and CI
stay green (the `EXTERNAL_TEST_DATABASE_URL` path too) **before** any importer work. If this proves much messier than expected,
stop and note it in STATUS rather than forcing it — the fallback is `packages/import` reaching the schema by relative path.

### 1. Schema additions (one new migration; do not edit S1's migrations)

S1's schema lacks what the ledger port needs. Add:
- `customers`: `opening_balance_p bigint not null default 0`, `opening_balance_date date`, `is_cash_counter boolean`,
  `legacy_code text`. `suppliers`: `opening_balance_p`, `opening_balance_date`.
- `invoices.invoice_number`, `purchases.purchase_number`, `returns.return_number` (text, indexed). Keep `status` as the legacy
  status string verbatim.
- `returns`: also the return's cash link and treatment, e.g. `treatment text`, `refund_payment_id uuid null` — check how a
  customer return with a REFUND treatment references its payment (S3's `editAmount` refusal depends on it). No such rows exist in
  the real data, so read the code, and represent it in the fixture.
- **`payments`** (id, legacy_id unique, direction `IN|OUT`, party_type `CUSTOMER|SUPPLIER`, party_id uuid (not FK — polymorphic;
  enforce with the importer + a CHECK on party_type), is_refund, amount_p, method, reference, note, payment_date date,
  status `POSTED|REVERSED` (text), receipt_number unique, received_by, created_at) and **`payment_allocations`** (id, payment_id FK,
  invoice_id FK null, purchase_id FK null, amount_p; CHECK exactly one of invoice_id/purchase_id). S3 builds the services on these
  tables; S2 only loads them.
- `journal_entries`: add `source_type text`, `source_id uuid` with a **unique index on (source_type, source_id)** so every
  posted document has exactly one findable entry (an original + its reversal use different `source_type`s, e.g. `PAYMENT` and
  `PAYMENT_REVERSAL`). Import must set `created_at` from the legacy `createdAt` (statement order depends on it — see §3).
- `legacy_doc jsonb` on customers, suppliers, invoices, purchases, returns, payments: the untouched legacy document. It makes
  "nothing silently lost" literally true and lets M2/M3 map more fields later without re-designing the import.
- Control accounts (seeded by migration or by the importer — pick one, document it): `CASH` (Cash/Bank, asset), `RECEIVABLES`,
  `PAYABLES`, `SALES`, `PURCHASES`, `RETURNS` (customer returns / supplier returns, contra), `OPENING_EQUITY`. **Use these as
  single control accounts with `party_type`/`party_id` on the journal *lines*** — not one account per shop (S1's per-account
  `party_id` column stays unused). A party's balance = Σ over its lines on the control account.

Keep enum-ish columns plain text (S1 decision), validated in Zod at the importer boundary.

### 2. The importer — `pnpm --filter @farooq/import import <backup.json>`

**Store classification (the fail-loudly guarantee).** Every store name in `data` must appear in exactly one of three
lists in code, each with a one-line reason; a store in none of them aborts the import naming the store:
- **Imported in M1:** `regions, warehouses, products, customers, suppliers, invoices, purchases, payments,
  paymentAllocations, customerReturns, supplierReturns, sequences`.
- **Deferred to a later milestone (counted, not loaded):** `invoiceItems, purchaseItems, customerReturnItems,
  supplierReturnItems, inventory, stockMovements, stockDocs, stockDocItems, orders, orderItems, expenses, landedCosts,
  landedCostExpenses, inventoryCostAdjust, employees, salaryPayments, millingJobs, millingJobItems, millingArrivals,
  supplierProducts, priceHistory, priceApprovals, costHistory, salesmen, accountAdjustments, documents, documentEdits,
  operations, auditLog, business`. Grep the old code to confirm that none of these feeds `Ledger.customer/supplier`
  (`accountAdjustments` in particular) — if one does, it moves to "imported".
- **Ignored by design:** `users` (credentials), `syncQueue`, `migrationBackups`, `meta`, `legacy` (old-app bookkeeping).

**Field classification for imported stores.** For each imported store, every key that appears on any document must be
classified `mapped`, `legacy_doc-only` (kept in the jsonb, with a reason) or `ignored` (with a reason); an unclassified key
aborts the import naming store + key. Also abort on: a non-integer or non-finite money field, a party/reference id that doesn't
resolve, a duplicate legacy id, an unknown `status`/`direction`/`partyType` value.

**Loading.**
- Wipe = `TRUNCATE` of the business + ledger tables only (master data, transaction tables, payments, allocations,
  journal_*, sequences). Never touch `users`, `sessions`, `role_permissions`, `audit_log`. Refuse to run unless the DB host is
  `localhost`/`127.0.0.1` (the plan is local-only; a flag can override it later). One transaction for the whole load; roll back on any error.
- Map master data (with `legacy_id` = the legacy `id`), then transaction headers, payments + allocations.
- Load the `sequences` store into `sequences(kind, year, n)` so S3's next receipt number continues from the live one
  (`REC`, `PV`, `INV`, `PUR`, `RCV`). Add a test that the loaded counters equal the backup's.
- Write one `audit_log` row (`IMPORT`, counts, source file name, `exportedAt`).

### 3. Journal entries — port the Ledger's *filters* exactly, not what seems logical

The ledger you are reproducing has quirks; reproduce them and record each in a code comment + test:

| Source document | Posted when | Entry (paisa) |
|---|---|---|
| Invoice | `status` not `DRAFT`/`CANCELLED` | DR `RECEIVABLES`(customer) `grandTotal` / CR `SALES` |
| Payment IN (customer receipt) | not `REVERSED` | DR `CASH` / CR `RECEIVABLES`(customer) |
| Payment OUT with customer party (refund) | not `REVERSED` | DR `RECEIVABLES`(customer) / CR `CASH` |
| Customer return | `status` not `CANCELLED` (**DRAFT counts**) | DR `RETURNS` / CR `RECEIVABLES`(customer) `creditAmount` |
| Customer opening balance | `openingBalanceP` ≠ 0 | DR `RECEIVABLES` / CR `OPENING_EQUITY` |
| Purchase | `status` not `CANCELLED` (**DRAFT counts**) | DR `PURCHASES` / CR `PAYABLES`(supplier) `grandTotal` |
| Payment OUT (supplier) | `partyType` not `CUSTOMER`, not `REVERSED` | DR `PAYABLES`(supplier) / CR `CASH` |
| Supplier return | `status` not `CANCELLED` | DR `PAYABLES`(supplier) / CR `RETURNS` `debitAmount` |
| Supplier opening balance | `openingBalanceP` ≠ 0 | DR `OPENING_EQUITY` / CR `PAYABLES` |

- **REVERSED payments:** import the row with `status='REVERSED'` **and** post both the original entry and a reversing entry
  (`source_type='PAYMENT_REVERSAL'`) so the net is zero and the shape matches what S3's `reverse` will produce. (The legacy
  ledger simply skips them; the net effect is identical — that equivalence is one of the things the fixture proves.)
- Journal `date` = the document's business date (`invoiceDate`, `paymentDate`, …; opening balances: `openingBalanceDate` or
  `2000-01-01`, as the legacy code does). `created_at` = legacy `createdAt` when present.
- A document that is skipped (DRAFT/CANCELLED) is still imported as a row, with no journal entry.
- Read the Ledger's exact conditions once more before coding — e.g. the customer-side payment filter is
  `direction==='IN' || partyType==='CUSTOMER'`, and refund rows have no `createdAt`. If you find the table above disagrees with
  the code, **the code wins** — fix the table in your STATUS entry.

### 4. `LegacyLedger` — the independent old-algorithm recompute

A literal TypeScript port of `Ledger.customer` / `Ledger.supplier` / `_roll` that runs **on the raw backup JSON in memory** —
no database, no calls into the importer or the new ledger. Independence is the point: two implementations built differently
must agree. Return closing balance and the ordered statement rows (with running balance), like the original. Sign convention:
customer balance positive = shop owes us; supplier balance positive = we owe them (`_roll(…, credited=true)`).

### 5. Reconciliation report

After the load, for **every** customer and supplier compare `LegacyLedger` closing balance vs the new ledger's
(`SUM(debit_p) - SUM(credit_p)` for customers, reversed for suppliers, on that party's `RECEIVABLES`/`PAYABLES` lines). Also:
- Σ debit == Σ credit across the whole journal (trial balance);
- per-store row counts: backup `counts` vs rows loaded (deferred/ignored stores listed as such);
- Σ balances per direction (receivables, payables) old vs new;
- a **statement check**: for each party the ordered (date, created_at) statement rows and running balances equal the legacy
  `_roll` rows (S4's statement screen relies on this). If tie-break order on equal keys is genuinely ambiguous, define the rule,
  document it, and say so — closing balance is the hard requirement; statement equality is required unless you document why not.
- an informational line (not failing): how many parties carry a nonzero legacy paper-book figure that was deliberately not posted.

Output: a human-readable report to stdout **and** `data/reconciliation-<timestamp>.json` (gitignored). Exit non-zero if any
party differs, the trial balance is off, or a count mismatches. The report must print real numbers (party counts, differences
found, totals in paisa), not just "OK".

### 6. Tests (all in CI, all against Postgres)

- **Synthetic fixture** committed under `packages/import/fixtures/` (fabricated names/ids/amounts — no real data), same envelope
  and the same *field names* as the real backup (copy the key sets from the real file, invent values). It must cover: customer
  and supplier **opening balances** with dates; invoices in each status (DRAFT, CANCELLED, CONFIRMED, PAID); several documents on
  the same day (tie-break); a payment IN with partial allocations; a **REVERSED** payment; a customer **refund** (OUT, `isRefund`);
  a supplier payment; a **customer return** (normal, and CANCELLED) and a **supplier return**; a **DRAFT purchase** and a
  CANCELLED purchase; a party with no activity; a cash-counter customer; Urdu (UTF-8) names; and the `sequences` store.
  Generate it with a small committed script if that's easier than hand-writing JSON.
- End-to-end: import the fixture into embedded-postgres → reconciliation shows **0 differences**, trial balance balanced,
  statement check passes, counts match.
- **The safety net must be shown to bite:** after a successful import, corrupt one journal line (change an amount) and assert
  the reconciliation reports that exact party and exits non-zero. Do the same for a missing entry.
- Fail-loudly tests: unknown store, unknown field in an imported store, non-integer money, dangling party id, duplicate
  legacy id, unknown status — each aborts with a message naming the store/field, and leaves the DB unchanged (rolled back).
- Idempotency: import twice in a row → identical row counts, identical balances.
- Guard tests: refuses a non-local DB host; never truncates `users`/`sessions`/`role_permissions`/`audit_log`.
- Unit tests for `LegacyLedger` on hand-computed expectations (write the expected numbers by hand from the fixture, don't
  derive them from the importer).

Run the importer + report against `data/business-20260922-210002-v505-6a81.json` on a local embedded-postgres. STATUS must

## Definition of done

- `pnpm build && pnpm typecheck && pnpm lint && pnpm test` green locally and in CI (Postgres service container).
- Fixture reconciliation: 0 differences on every party, trial balance balanced, statement check passing (or the documented exception).
- Real-backup reconciliation: 0 differences for all 409 customers and 35 suppliers, with the real totals written into STATUS.
- The tests that prove the safety net bites and the importer fails loudly all exist and pass.
- No real business data or credentials in git (`git status` clean of `data/`; `users` store never read into the DB).
- STATUS.md updated: what's done, actual numbers, deviations from this plan (especially anywhere the Ledger code disagreed with
  the posting table above), known issues, and "next: S3".
- Nothing uncommitted; pushed to `origin main`.

## Out of scope

- Payments *operations* (receive/pay/refund/reverse/editAmount), receipt-number allocation, permission guards — S3.
- Any UI — S4. Invoice/purchase **line items**, stock, costs, payroll, milling — later milestones (their stores are counted,
  not loaded).
- Posting the legacy paper-book balances / choosing an opening-balance cutover date — needs the owner (old `CLAUDE.md` open item 1).
- Importing users/passwords. Any write to the live server or its databases. Any deployment.
