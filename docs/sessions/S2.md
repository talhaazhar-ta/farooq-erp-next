# S2 — Importer + reconciliation

## Goal

Build `packages/import`: a tool that reads a legacy backup JSON file and loads it into the Postgres schema
from S1, then prints a reconciliation report proving the new ledger reproduces the old app's balances. This is
the "will the migration be 100%?" safety net — read `CLAUDE.md` rule 8 before starting.

**Prerequisite:** S1 must be done (`docs/STATUS.md` should say so, and `pnpm test` should be green on `main`
before you start). If S1 isn't done, stop and say so instead of improvising the schema.

## Scope

### 1. Backup format

The input is the same `farooq-co-erp-backup` JSON format that `scripts/backup-business-db.php` in the old
project (`D:\projectFarooqAndCoTraders`) writes. Read that script and a sample backup structure (ask the user
for a real nightly backup path, or generate/request a synthetic one, if you need to see the shape — don't
guess field names). Also read `D:\projectFarooqAndCoTraders\docs\SERVER_DATA.md` for how the 46 stores map to
JSON documents.

### 2. Importer (`pnpm import <backup.json>`)

- Maps each store (customers/shops, suppliers, regions, products, warehouses, invoices, purchases,
  customerReturns, supplierReturns, payments, opening balances) to the S1 schema.
- Builds journal entries for: opening balances, invoices (Receivables debit / Sales credit), purchases
  (Purchases debit / Payables credit), returns, and payments (per `02-services.js`'s existing posting logic —
  read it, don't reinvent the accounting).
- **Idempotent**: running it again wipes and reloads the target database rather than accumulating duplicates.
- **Fails loudly** on any field/store it doesn't recognize — never silently drops data (this is the load-
  bearing guarantee from `CLAUDE.md` §"Two projects side by side"). A new/unmapped field must stop the import
  with a clear error naming the field and store.
- Never writes to the live server or its database. The backup file is read from disk only. If you need a real
  backup file, ask the user to fetch it — `docs/OPERATIONS.md` in the old project documents the read-only SSH
  path (`~/backups/nightly/*.json`); this project must not SSH to the old server itself unless the user
  explicitly directs it for this one read.
- Backup JSON files and anything derived from them live under `/data/` (gitignored, see `.gitignore`) — never
  commit real business data.

### 3. Legacy ledger port (`LegacyLedgerService` or equivalent, in `packages/import` or `apps/api`)

Port `Ledger.customer` / `Ledger.supplier` from `D:\projectFarooqAndCoTraders\public_html\ERP\erp-upgrade\
02-services.js` (read the actual line range — the old project's CLAUDE.md cites `02-services.js:1742-1824` as
of 2026-09, but re-locate it since the file may have moved since). This exists **purely for reconciliation**:
it recomputes each party's balance the old, document-scanning way, so it can be diffed against the new
ledger's balance for the same party. Keep the two implementations independent — the point is that they must
agree despite being built differently, not that one calls the other.

### 4. Reconciliation report

For every shop and supplier: old-algorithm balance vs new-ledger balance, the difference (should be 0), plus
totals and row counts per store, and the list of any unmapped fields encountered. Exit non-zero on any
non-zero difference. Print (or write to a file) numbers the planning-hub session can quote verbatim in
STATUS — don't just print "OK".

### 5. Tests

- A committed **synthetic fixture** backup (small, fabricated data, no real business data) under
  `packages/import/fixtures/` or similar, used by an automated test that runs the importer end-to-end against
  embedded-postgres and asserts the reconciliation report shows 0 differences.
- Unit tests for the field-mapping and the fail-loudly-on-unmapped-field behaviour (feed it a fixture with a
  deliberately unknown field, assert it throws).

## Steps (suggested order)

1. Get one real (or realistic synthetic, if a real one isn't available yet) backup file and read its actual
   shape before writing any mapping code — do not guess field names from memory of the old app's code alone.
2. Build the store→schema mapping for master data first (customers, suppliers, regions, products,
   warehouses), then the transactional stores (invoices, purchases, returns, payments, opening balances).
3. Build the journal-entry construction for each transactional store.
4. Build `LegacyLedgerService` (the independent old-style balance calculation).
5. Build the reconciliation report and wire up the non-zero exit code.
6. Write the synthetic fixture + its test.
7. Run against a real nightly backup if the user provides one; record the actual reconciliation numbers.

## Definition of done

- `pnpm import <backup.json>` runs against embedded-postgres in a test and reports **0 balance differences**
  on the committed synthetic fixture.
- If a real nightly backup was available this session: the same 0-difference result was reproduced against
  it, and the actual shop/supplier counts and any totals are recorded in STATUS (not just "passed").
- An unmapped field in a test fixture causes the importer to fail loudly, with a test proving it.
- No real business data committed to git — confirm `/data/` is gitignored and `git status` shows nothing
  business-data-shaped staged.
- `docs/STATUS.md` updated per the usual template (done / verification numbers / deviations / known issues /
  next: S3).
- Nothing uncommitted; pushed to `origin main`.

## Out of scope

- The Payments service/API itself (S3) — this session only needs enough of the payments *shape* to import
  historical payment records and post their journal entries; it does not build receive/pay/refund/reverse/
  editAmount as callable operations.
- Payments UI (S4).
- Any deployment or write access to the live server/database.
