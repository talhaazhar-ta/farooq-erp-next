|---|---|---|

From the first post-wipe nightly on, that means near-empty data, so every real-data proof (balances, invoices, purchases, average cost, search parity) would quietly go trivial. |

## Scope and rules (each gets a test)

### 1. Sale cost = stock cost + extra cost per bag (`c78659b`)
- **`extraOf(product, basis)`**, a pure function in `@farooq/shared`:
  - returns `0` under the `PURCHASE` basis;
  - otherwise returns `products.extra_p` when set (> 0), else 0.
  - The legacy's rupee `extra` fallback: S6's importer already resolves `Prices.of` precedence into `extra_p`. Prove that with one importer test, rather than re-porting the fallback.
- **`saleCostOf`** = `costOf + extraOf` **only when `costOf` > 0**. An unknown stock cost stays unknown (0 / "cost unknown"), because the extra alone is not a cost price.
  - Put it next to `costOf` in `apps/api/src/invoices/stock.ts`. The basis comes from `readProfitCostBasis`.
- **Every place that snapshots or shows a sale's cost uses it:**
  - the invoice post / edit `cost_snapshot_p` (`invoices.service.ts` ~496);
  - `GET /products` `costP` for `PROFIT_VIEW` (`invoices.queries.ts` ~319);
  - the builder's price hints.
  - If the legacy note's breakdown ("stock X + extra Y") is shown, return `stockCostP` and `extraP` beside `costP` (still only with `PROFIT_VIEW`, absent otherwise) and copy the legacy wording verbatim.
- **Old invoices keep their snapshot.** Nothing is recomputed, and the importer still imports `costSnapshot` as stored.
- **Not affected** (prove each with a test): `stock_levels.avg_cost_p`, the purchase average (S11 / S12), `last_cost_p`, and the purchase detail's `costs` block.
- **Profit (`@farooq/shared` `profit.ts`) reads the snapshot**, so it follows automatically. Add one end-to-end test: a product with `extra_p` 200 and stock cost 3,000 sold at 3,500 → profit 300 a bag, not 500 (the client's own example, in paisa).

### 2. `RECEIPT_EDIT_OUT` and the carried cost (`b2b0778`)
- **`packages/db` `stock.ts`:** add `RECEIPT_EDIT_OUT` to `MOVEMENT_KINDS` and `STOCK_RECEIPT_EDIT` to the ref types. Check whether a migration is needed (enum-shaped columns are plain `text`, validated at the boundary; say what you found).
- **Importer:** accept the kind and ref type, with fail-loudly tests updated. A `RECEIPT_EDIT_OUT` has `qty_delta < 0` and carries a `unit_cost_p`; refuse one that doesn't, as a new fail-loudly case.
  - `source_type`: map it like the other stock-document movements (`STOCK_RECEIPT` today). Say what the real refType / ref look like.
- **`carriedCost`** (`apps/api/src/invoices/stock.ts`) = the legacy's new rule exactly:
  - skip the damaged bucket and `unit_cost_p` ≤ 0 / NULL;
  - a `RECEIPT_EDIT_OUT` with qty < 0 **subtracts** qty × its cost;
  - otherwise count only the carried kinds with qty > 0;
  - the result is `round(cost / qty)` only when **both** the qty and the cost are > 0, else 0.
- **Hand-computed test from `test-receipt-edit.mjs`:** a receipt of 10 @ 500, edited to 10 @ 600 → carried 600, not 550. Also add a receipt edited down to 0 lines.
- **Reconciliation:** stock levels = Σ movements already covers the new kind. Add a fixture case (one receipt edit in `build-fixture.ts`, hand-computed) so the importer, `carriedCost` and `costOf` see one. The fixture drift test must pass.
- **Not in scope:** editing a receipt in the rebuild (stock documents are M4). Add a PARITY row pointing M4 at `StockDocs.editReceive`.

  - Put the list in one shared helper (`@farooq/db/testing` or `packages/import/test/helpers`) so this never drifts again.
- **Fetch the first post-wipe nightly** (read-only, one `scp` into the gitignored `data/`; the cron runs 02:00 Pakistan time). The importer must accept it with **0 differences**.
  - It has near-empty transactions but the kept master data, and customers / suppliers with zeroed cached balances. Say what you see: counts only, never rows.
