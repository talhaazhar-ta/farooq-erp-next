## Decisions already made (the planner's calls — record them in STATUS, don't reopen without a reason)

1. **Statement order:** business date → `journal_entries.created_at` → entry id; for **customers the OPENING row first whatever its
   date** (legacy 16-khata). We do **not** copy the legacy quirk that rows without `createdAt` (refunds, supplier payments, returns,
   openings) sort before same-day invoices — that is an artefact of missing data, not intent. Closing and end-of-day balances are
   identical; only the running balance *between* same-day rows can differ (the reconciliation already reports this as informational).
2. **Reversed vouchers** (original + reversal entry) are **omitted** from statements, as in the legacy; a `omittedReversed` count is returned
   so the UI can say "n reversed vouchers hidden". An edited voucher is one row at its current amount.
3. **Receipt balances:** the receipt shows *Previous balance* and *Remaining balance* = the party's running balance immediately **before /
   after that voucher's row in the statement order above** (deterministic, so a reprint next month shows the same figures). The legacy
   showed a stale stored `balanceBefore` and the *current* balance — record this deviation. A REVERSED voucher's receipt has no balances
   and is stamped Reversed.
4. **Party names on a voucher are snapshots** (legacy `partyNameSnapshot` etc.): what was printed then. Add `party_name_snapshot`,
   `party_owner_snapshot`, `region_snapshot` to `payments` (filled by the service at creation; by the importer from the legacy doc
   fields of the same name). Receipts print the snapshot; search matches the snapshot **and** the party's current name (legacy does both).
5. **No Postgres extensions** (no `pg_trgm`, `unaccent`): the embedded test Postgres and the CI service container may not have them.
   Folding is a plain SQL function (§2).
6. **Money entry parsing is strict:** more than 2 decimal places is an error (the legacy `toPaisa` silently rounds). Parse from the string,
   never through floating point (`1.005`, `0.1 + 0.2`).
7. Amount in words follows the legacy style and **also says the paisa** ("… Rupees and Fifty Paisa Only") — the legacy rounded to whole rupees.
8. Search is **server-side** (Postgres); the server parses the raw `q` (shared code) and echoes back how it read it.

## Scope

### 1. `packages/shared` — pure, unit-tested helpers (port the legacy tests' cases)
- `fold.ts`: `foldSearch(s)` = legacy `normalize` (lower-case, Urdu/Arabic letter variants ک/ك, ی/ي/ى, ہ/ه/ھ… folded, harakat stripped,
  non-letter/digit → single space, trimmed). Also `hasTerm`-style helper: a term matches if the field contains it, or — for a multi-word
  term — the field contains it with spaces removed.
- `search-query.ts`: `parseSearchQuery(raw)` → `{ terms, dates[] }`, a faithful port of legacy `parse` (Arabic-Indic and Persian digits;
  `2026-09-12`; `12/09/2026` day-first with month-first only when that is the sole valid reading; `12 Sep 2026`; `Sep 12, 2026`;
  `Sep 2026`; `2026 Sep`; `2026-09`; `09/2026` only as words of their own; 2-digit years; range 1990–2100), each date → `{from,to,label,src,dayFirst}`.
  Labels in the legacy format (`fmtDate`). Never through `Date`/`toISOString()`.
- `money.ts`: `parseRupees(text)` → paisa or an error (accepts commas/spaces/`Rs`/`PKR`; rejects negative, non-numeric, > 2 decimals, > `MAX_AMOUNT_P`),
  `formatPaisa(p)` (en-US grouping; `.00` only when there are paisa — match the legacy `M.fmt`), `amountInWords(p)` (legacy `words`, then the paisa clause).
- Zod schemas + types for every new response below (S5 imports them; requests are `.strict()`).

### 2. Migration `0004` (earlier migrations untouched) + importer follow-through
- SQL function `fold_search(text) RETURNS text IMMUTABLE` implementing exactly the same folding as `foldSearch` (translate + regexp_replace).
  A **parity test** feeds a corpus (Urdu variants, diacritics, digits, punctuation, mixed scripts, empty/NULL) through both and demands identical output.
- `payments.party_name_snapshot / party_owner_snapshot / region_snapshot` (text, nullable). Service fills them at creation (S3 code; add tests);
  importer maps the legacy fields (classification: `mapped`). Nothing else about balances changes.
- `company_profile(id text primary key, doc jsonb not null, updated_at)`; the importer loads the backup's `business` store (one row, ~60 settings
  keys) **verbatim** into it. Classification: `business` moves from *deferred* to *imported — verbatim settings blob* (say why no field-level
  check: it is a settings bag, the app reads it whole). **Fail loudly** if any key name looks like a credential
  (`/pass|secret|token|api.?key|pin/i`) — test it. Add `business` to the loader's wipe list.
- Indexes only if a query plan needs one (data is small).

### 3. API additions (all in `apps/api/src/payments/` or a sibling `statements/`; permission = the S3 any-of
`PAYMENT_CREATE | COLLECTION_VIEW | FINANCIAL_REPORT_VIEW` unless stated; INVENTORY gets 403)

**a. `GET /payments` v2** — extends S3's endpoint (keep existing params working):
`q` (raw), `scope` (`all|number|party|reference|invoice|amount|notes`), `direction` (`all|received|paidToShops|paidToSuppliers` — keep S3's
`direction`/`partyType` params valid), `status`, `method`, `regionId`, `from`/`to`, `minP`/`maxP`, `sort` (`newest|oldest|high|low`), `limit` (default 50, max 200), `offset`.
- Each search term must match (AND, any order) in the scope's folded fields. Fields, as in legacy: **number** (receipt no. + compact form),
  **party** (snapshot name/owner/region **and** current name, owner, phone + compact, region, legacy code), **reference** (+ compact),
  **invoice** (numbers of the invoices/purchases the voucher was applied to + compact), **amount** (all typed forms: `1000`, `1,000`, `1000.50`, `1,000.50`),
  **date** (`2026-09-12`, `12 Sep 2026`, month name…), **other** (note, method, received-by, type words `receipt`/`refund voucher`/`voucher`,
  and for reversed vouchers `reversed cancelled <reason>`). `all` = every field.
- A date typed in `q` becomes a date filter (replacing `from`/`to`, as legacy) and is **echoed**: response `interpreted: { terms: string[], dates: {label,from,to}[], problems: string[] }`
  where `problems` carries the legacy messages for inputs that can never match (From after To, min above max) — say it out loud instead of returning an empty list quietly.
- Response also has `facets`: `{ received, paidToShops, paidToSuppliers, reversed }` each `{ count, totalP }`, computed with every filter **except** `direction`/`status`
  (so the S5 tabs can show counts). Reversed vouchers belong to the `reversed` facet only, as in legacy.
- **Parity proof:** write a JS *reference implementation* (test helper) of legacy `build` + `match` over the legacy-shaped JSON, and assert the endpoint returns
  the **same ids in the same order** for a table of ~40 queries (single/multi word, Urdu variants, typed dates, each scope, amount forms, invoice numbers, method, reversed).
  The real backup has only 7 payments, so also generate a **deterministic seeded synthetic backup with ~300 payments** (all directions/methods/statuses, allocations,
  Urdu and English names) in the test, import it through the importer, and run the same table against it. Include paging (offset/limit stitch = the full list) and sorts.

**b. `GET /payments/export.csv`** — same filters, no paging, every match. Columns as the legacy CSV (read 38); UTF-8 **with BOM** (Excel + Urdu);
RFC-4180 quoting; **spreadsheet-injection guard** (a cell starting `= + - @ TAB CR` gets a leading `'`); `Content-Disposition` filename with the business date. Tests incl. an Urdu name, a comma/quote/newline in a note, a `=cmd` reference.

**c. `GET /customers/:id/statement?from&to` and `GET /suppliers/:id/statement?from&to`** — built from the journal (party lines on RECEIVABLES/PAYABLES joined to the
source document for number/method), per decisions 1–2. Response: `party` (name, owner, region, phone), `opening` (balance before `from`; the OPENING row of a customer is an ordinary row when in range),
`rows[{ date, createdAt, kind, ref, description, debitP, creditP, balanceP, source:{type,id} }]`, `totals`, `closing`, `omittedReversed`. Row descriptions are the legacy strings (list above; adjustments per 16-khata; milling per 32-milling).
Debit/credit columns follow the legacy (customers: invoice/refund = debit, receipt/return = credit; suppliers: purchase = credit, payment/return = debit), which is the journal's own side on RECEIVABLES/PAYABLES.
- **Proof:** for every customer and supplier of the fixture **and** the real backup, the statement's closing balance and the multiset of rows `(date, kind, ref, signed amount)`
  equal `LegacyLedger`'s (S2), for the full range and for a mid-range `from`/`to` (opening = balance before `from`); running balances telescope (`opening + Σ = closing`).

**d. `GET /payments/:id/receipt`** — the receipt/voucher model: company block (from `company_profile`: business name, tagline(s), slogan, logo text, address, city, phones, whatsapp, proprietor, currency label, receivedBy label), `kind` (`RECEIPT` for IN, `VOUCHER` for OUT), title
(`PAYMENT RECEIPT` / `PAYMENT VOUCHER`), `RECEIVED FROM` / `PAID TO` party block (snapshots, + current phone for customers), meta (receipt no., date, method, reference, received by), allocation rows (invoice/purchase number, its date, amount applied; or `On account`), total applied, amount, `amountInWords`, `previousBalanceP`/`remainingBalanceP` per decision 3, notes, `status`/`cancelled`. Legacy titles and labels verbatim.

**e. `GET /company`** — the whitelisted display fields only (never the whole settings bag). **`GET /regions`** (`MASTER_DATA_VIEW`). Extend `GET /customers` lookup with `regionId`.
