# S4 — Payments UI + statements

## Goal

Build the Payments screens on top of S3's API: list/search, the 5 actions (receive/pay/refund/reverse/
editAmount), a receipt print view, and a read-only shop/supplier statement — then prove it with Playwright e2e
tests and a real walkthrough in headless Chrome. This closes out Milestone 1.

**Prerequisite:** S1–S3 done (`docs/STATUS.md` should confirm all three). If not, stop and say so.

## Scope

### 1. Payments list/search

Port the useful behaviour of `D:\projectFarooqAndCoTraders\public_html\ERP\erp-upgrade\38-payment-search.js`
(day-first numeric date parsing — read the old project's `CLAUDE.md` note: "Invoice search (33) and Payment
search (38) share `ERP.InvoiceSearch.util`; numeric dates are day-first"). Build with TanStack Table +
TanStack Query against S3's list/search endpoint. Paging for long lists (the old app pages anything over 48
rows — match that threshold or note why you chose differently).

### 2. The 5 actions as UI flows

Receive payment, Pay a shop, Pay supplier, Reverse, Edit amount — each calling the matching S3 endpoint.

- **Money screens never pre-select a party** (`CLAUDE.md` rule, ported from the old app): every one of these
  starts on a blank "— Choose … —" state; the client-side Save button must be disabled/refuse without a
  party chosen, in addition to (not instead of) S3's server-side refusal.
- Permission-gate the buttons using `packages/shared` constants (hiding a button a user has no permission for
  is a UX nicety; S3's guard is the real enforcement — don't skip the server check because the button is
  hidden).
- Edit amount: surface S3's three refusal reasons as real user-facing messages, not a generic error.

### 3. Receipt print view

A printable view for a posted payment voucher (receipt number, party, amount, date, method). Doesn't need to
pixel-match the old app's print output, but must be genuinely printable (test print-to-PDF in headless
Chrome, not just screen rendering).

### 4. Shop / supplier statement

Read-only running balance view, backed by the real ledger (the same balance S3's read endpoint exposes).
This is also your own eyeball check that S2's reconciliation and S3's posting agree in the UI, not just in
tests.

### 5. Tests

- Playwright e2e covering: sign in → receive a payment → it appears in the list/search → reverse it → status
  updates → edit-amount is refused on the now-reversed voucher with the right message.
- A second e2e path for pay-a-supplier and pay-a-shop money-out flows.
- Run in headless Chrome (per this repo's `CLAUDE.md`, not yet an established local-preview pattern beyond
  what S1 set up — reuse S1's approach or document why you needed something different).

## Steps (suggested order)

1. Payments list/search UI against S3's list endpoint.
2. Receive payment flow (blank-party rule, S3 call, appears in list).
3. Pay-a-shop / Pay-supplier flows (similar shape to receive).
4. Reverse flow.
5. Edit-amount flow with the three real refusal messages.
6. Receipt print view.
7. Shop/supplier statement.
8. Playwright e2e for the two paths above.
9. Manual walkthrough in headless Chrome with screenshots; write down plainly what was and wasn't seen by a
   person (this repo has no physical-device testing yet — say so, the way the old project's CLAUDE.md tracks
   "not yet seen on the live site").

## Definition of done

- Playwright e2e green for both paths in step 8/9.
- Screenshots (or a description of what was seen) from the headless-Chrome walkthrough recorded in STATUS.
- `docs/STATUS.md` updated with an explicit "not yet seen by a person" list (mirroring the old project's
  section of the same name) for anything this session didn't actually click through.
- Milestone 1 is complete: STATUS.md should say so plainly, and summarize the M1 reconciliation numbers from
  S2 one more time for a fresh reader who didn't see S2's own STATUS entry.
- Nothing uncommitted; pushed to `origin main`.

## Out of scope

- Invoice/purchase screens (M2/M3) — Payments here only reads existing imported header totals for allocation
  context; it doesn't build invoice or purchase creation/editing.
- Any deployment or hosting decision.
- Mobile/tablet/physical-device testing beyond whatever headless Chrome's viewport emulation covers.
