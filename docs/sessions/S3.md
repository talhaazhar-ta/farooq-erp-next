# S3 — Payments service + API

_Rewritten by the planning hub after S2, against the legacy code (`02-services.js` `Payments`, `Invoices.outstanding` /
`refreshPaymentState`, `FDB.nextNumber`) and S2's real schema._

## Goal

Server-side `PaymentsService` in `apps/api`: **receive / pay / refund / reverse / editAmount**, each in one DB
transaction, each enforcing its rules on the server (not in the browser), each posting the right journal entry and an audit
row, plus the small read API the S4 screens need. This is the "rules checked only in the browser" problem the rebuild exists
to fix (`CLAUDE.md` rule 7). No UI (S4).

**Prerequisite:** S1 + S2 done. Run `pnpm install && pnpm build && pnpm test` first; expect 101 green. Read
`docs/STATUS.md` (S2's "Next step" section and deviations 5–6), `packages/db/src/schema.ts`, and the `prepareImport`
doc comment + `custLine`/`supLine` in `packages/import/src/prepare.ts`.

## The legacy code you are porting (read it — don't work from this summary alone)

`D:\projectFarooqAndCoTraders\public_html\ERP\erp-upgrade\02-services.js`: `var Payments` (~line 1257–1442),
`Invoices.paidFor / outstanding / refreshPaymentState` (~835–860), `Calc.paymentStatus` (~280); `01-db.js`
`FDB.nextNumber` (~294). Things the code does that the earlier plan text did not say:

- **`receive` does not cap explicit allocations.** With chosen allocations the legacy passes them straight through; only the
  UI limits them. `autoAllocate` (oldest invoice first, non-DRAFT/CANCELLED, outstanding > 0) is the only place outstanding
  is respected. **The server must enforce it** (see §2) — a deliberate, recorded *stricter-than-legacy* change.
- **`Invoices.outstanding` = grandTotal − Σ allocations − Σ credit of non-CANCELLED customer returns linked to that invoice**
  (`returns.invoiceId`). S2 kept `invoiceId` only inside `returns.legacy_doc`, so S3 needs a new column (§1).
- **Allocation changes the invoice's `status`:** `refreshPaymentState` sets `CONFIRMED`/`PARTIALLY_PAID`/`PAID` from
  `Calc.paymentStatus(grandTotal, paid)` (`paid >= grand` → PAID; `paid > 0` → PARTIAL; grand ≤ 0 → UNPAID) — but leaves
  `CANCELLED`, `DRAFT`, `RETURNED`, `PARTIALLY_RETURNED` alone. Note `paid` here is allocations only (returns credit is *not*
  subtracted for the status). Mirror this exactly on the `invoices.status` column; it is what S4's lists will show.
- **`reverse` sets `status=REVERSED` and deletes the payment's allocation rows**, then refreshes invoice state. There is **no
  legacy UI that calls it** (only the engine function) and it does **not** refuse an already-reversed voucher.
- **`editAmountCheck`** refusals, in this order, with these exact messages (S4 shows them, keep them verbatim):
  1. not found → `Payment not found.`
  2. `REVERSED` → `A reversed voucher cannot be edited.`
  3. not (`OUT` to a `CUSTOMER` or `SUPPLIER`) → `Only a voucher paid to a shop or a supplier can have its amount corrected here.`
  4. has any allocation → `This payment is applied to an invoice or purchase; its amount can’t be changed here.`
  5. customer voucher whose note starts `Refund against return ` and whose `reference` equals some customer return's number →
     `This voucher is the refund for a customer return — correct the return instead.`
  then amount must be > 0 (`Enter an amount greater than zero.`) and different from the current one
  (`That is already the recorded amount.`). It changes `amount` in place; the ledger reads the live amount.
- **Receipt numbers**: kind `REC` for IN (the legacy has a `receiptPrefix` setting defaulting to `REC` — hard-code `REC`; there
  is no settings module yet), `PV` for OUT; format `<KIND>-<YYYY>-<6-digit n>` (`REC-2026-000001`); year = the **current**
  year (not the payment date). The legacy takes the number **inside the same transaction** as the payment, so a rolled-back
  save does not consume a number (S1's STATUS says gaps mean "an attempt happened" — for payments that is not what the legacy
  does; fix that note in your STATUS if you agree).
- `pay`'s allocations are optional purchase allocations (`purchaseId`); the legacy never refreshes a purchase's payment state
  from `_write` (only `reverse` does). `refund` is `_write(..., 'OUT')` with `partyType:'CUSTOMER'`, `isRefund:true`, no allocations.
- The legacy stamps `balanceBefore/After` on the payment. **Do not port** them (derived data; the ledger is the truth).

## Scope

### 1. Migration `0003` (do not edit earlier migrations) and importer follow-through
- `returns.invoice_id uuid references invoices` (nullable, indexed). Update the importer (`classification.ts` / `prepare.ts`:
  `invoiceId` moves from `docOnly` to `mapped`) and its tests; the reconciliation must stay 0 differences.
- `payments`: check what S2 already has, then add what's missing: `created_by uuid references users`, `reversed_at`,
  `reversed_by`, `reverse_reason text`, and `idempotency_key text unique` (nullable; the legacy has no guard against a
  double-clicked Save on payments — a second POST with the same key must return the *first* result, not create a second
  voucher). Also an index for the list screen (`payment_date desc, created_at desc`) and on `payment_allocations(payment_id)`,
  `(invoice_id)`, `(purchase_id)` if absent.
- New permission **`PAYMENT_PAYOUT`** in `packages/shared` (single source of truth), granted to OWNER (implicit), MANAGER,
  ACCOUNTANT — **not** SALES/INVENTORY. It gates `pay` and `refund`. Reason: legacy open item 7 — the `SALES` role has
  `PAYMENT_CREATE` and could record cash paid *out*. This is a deliberate behaviour change, flagged in STATUS + PARITY as an
  owner decision (flip it by editing the role map). `receive` needs `PAYMENT_CREATE`; `reverse` and `editAmount` need
  `TRANSACTION_CORRECT` (the legacy gates edit-amount with it; reverse has no legacy UI gate). Add tests in `permissions.test.ts`.

### 2. `PaymentsService` — all rules server-side, one transaction each

Inputs are **integer paisa** (`amountP`), never rupee decimals (the UI converts). Dates are `YYYY-MM-DD` **business dates**;
default = today in **Asia/Karachi** (not the server's zone, not `toISOString()` — `CLAUDE.md` rule 6; inject a clock so a test
can prove `2026-01-01T20:00:00Z` → `2026-01-02`). Validate with Zod schemas that live in `packages/shared` (`payments.ts`:
request + response shapes) so S4 imports the same types. Reject unknown fields.

**receive** (money in from a shop; `PAYMENT_CREATE`)
- `amountP` integer > 0 (also cap it sanely, e.g. ≤ 10¹³); customer must exist (`Choose a shop.`); method/reference/note trimmed,
  length-limited.
- No `allocations` → auto-allocate oldest first: customer's invoices not DRAFT/CANCELLED with outstanding > 0, ordered by
  `date`, then `created_at`, then invoice number (the legacy sort is unstable on ties — define the tie-break, test it).
- With `allocations` → **server checks (new, stricter than legacy):** every invoice exists, belongs to *this* customer, is not
  DRAFT/CANCELLED, each `amountP` is an integer > 0 and ≤ that invoice's current outstanding, no duplicate invoice ids, and
  Σ allocations ≤ `amountP`. Lock the invoice rows (`SELECT … FOR UPDATE`, ordered by id) before computing outstanding so two
  concurrent receipts cannot both fill the same invoice.
- Any excess over what is allocated stays as an unallocated advance (legacy allows it) — it still credits the ledger.
- Writes: payment row (`POSTED`, `REC-…` number), allocation rows, `invoices.status` refresh for each touched invoice,
  journal entry (§3), audit row. Returns the voucher with its allocations.

**pay** (money out to a supplier; `PAYMENT_PAYOUT`): amount > 0; supplier exists (`Choose a supplier.`); `PV-…` number;
optional purchase allocations with the same guards (purchase belongs to the supplier, not CANCELLED, ≤ outstanding = total −
Σ allocations of POSTED payments, Σ ≤ amount). Do **not** touch `purchases.status` (purchase payment state is M3).

**refund** (money out to a shop; `PAYMENT_PAYOUT`): amount > 0; customer exists; `OUT`, `party_type=CUSTOMER`, `is_refund=true`,
`PV-…`; no allocations.

**reverse** (`TRANSACTION_CORRECT`): lock the payment row; refuse if not found or **already REVERSED** (new — the legacy
doesn't); set `REVERSED` + `reversed_at/by/reason` (reason required, non-empty); post the reversing journal entry; **keep** the
allocation rows (never delete money history — an `audit_log.before` snapshot holds them too) and make every "paid /
outstanding" computation count allocations of `POSTED` payments only; refresh the affected invoices' `status`. Legacy allows
reversing a customer-return refund voucher; keep that, note it. **Reversal journal date = the original payment's date** (S2
deviation 6: the pair cancels at every date and statements omit both, as the legacy ledger does). Say in STATUS that this
decision is now made for new activity too, and that there is no period locking (there is none in the legacy either).

**editAmount** (`TRANSACTION_CORRECT`): the refusals above, same order, same messages; change `amount_p` in place **and
rewrite that payment's journal entry lines to the new amount in the same transaction** (the legacy "corrects the figure in
place"; a delta-entry design would make statements show two rows — record this trade-off in STATUS). Audit `before/after`
(`amount`) + reason. For rule 5 use the FK `returns.refund_payment_id` **and** the legacy heuristic (note prefix + reference
== a customer return's number) — refuse if either matches, so it is never looser than legacy.

**Numbering** — one helper `nextNumber(tx, kind, year)`: `INSERT … ON CONFLICT (kind, year) DO UPDATE SET n = sequences.n + 1
RETURNING n` (atomic; serialises concurrent takers), inside the caller's transaction; format `KIND-YYYY-000001`. The importer
already loaded the live counters, so the first new receipt continues the live series. Test: N parallel receives → N distinct,
gap-free, sequential numbers; and a rolled-back receive does not consume one.

**Errors:** business-rule refusals → HTTP 422 `{ message, errors: string[] }` using the legacy wording; not found → 404;
missing/insufficient permission → 401/403 (guards, never the service); idempotent replay → 200 with the original voucher.

**Audit** (same transaction, `entity:'Payment'`): `Payment received`, `Refund paid to shop`, `Payment made to supplier`,
`Payment reversed`, `Payment amount corrected` — actor = session user, `before`/`after` as in the legacy.

### 3. One source of truth for posting shapes
The importer (`prepare.ts`) and the service must post **identical** lines. Extract the payment posting builder (the
`custLine`/`supLine` shapes: IN = DR CASH / CR RECEIVABLES(customer); refund = DR RECEIVABLES(customer) / CR CASH; supplier
payment = DR PAYABLES(supplier) / CR CASH; reversal = the mirror lines with `source_type='PAYMENT_REVERSAL'`, same
`source_id`) into a small shared module in `packages/db` (or a new `packages/ledger`) and make **both** import it. The 86
importer tests must stay green unchanged. Every posted payment has exactly one entry findable by `(source_type, source_id)`;
`journal_entries.created_by` = the session user.

### 4. Read API for S4 (small, read-only)
- `GET /payments` — server-side filter + paging: `q` (receipt number / party name / reference, case-insensitive), `direction`,
  `partyType`, `partyId`, `status`, `from`/`to` (business dates), `limit`/`offset`; order = `payment_date desc, created_at desc`;
  response includes party name, allocation summary and a total count. (S4 layers the day-first numeric-date search UX of module
  38 on top; don't build that here.) `GET /payments/:id` — the voucher + allocations (+ invoice/purchase numbers) + a flag
  telling the UI which actions the caller may take and *why an action is refused* (`editAmount` refusal reason) so the UI
  doesn't have to duplicate the rules.
- `GET /customers?q=&limit=` and `GET /suppliers?q=&limit=` (picker lookups: id, name, owner/contact, region, active) —
  `MASTER_DATA_VIEW`.
- `GET /customers/:id/balance`, `GET /suppliers/:id/balance` — from the **journal** (Σ lines on RECEIVABLES/PAYABLES for the
  party; positive = shop owes us / we owe the supplier), same definition the reconciliation uses.
- `GET /customers/:id/outstanding-invoices`, `GET /suppliers/:id/outstanding-purchases` — the rows the Receive/Pay panels
  allocate against (number, date, total, paid, outstanding), oldest first, using the same outstanding formula as the service.
- Read endpoints require any of `PAYMENT_CREATE | COLLECTION_VIEW | FINANCIAL_REPORT_VIEW` (add an any-of guard helper);
  INVENTORY (the warehouse role) must get 403.
- No statement endpoint (S4 decides ordering — S2 deviations 5/6).

### 5. Tests — one per rule, written from the legacy rules (hand-computed expectations, not copied from the code under test)

All against embedded Postgres (and the `EXTERNAL_TEST_DATABASE_URL` path in CI). At minimum:
- **receive:** amount ≤ 0 / non-integer rejected; missing or unknown shop rejected; auto-allocation is oldest-first incl. the
  tie-break; skips DRAFT/CANCELLED and other shops' invoices; stops at outstanding; excess stays unallocated; explicit
  allocation rejected when > outstanding, wrong customer, DRAFT/CANCELLED, duplicated invoice, or Σ > amount; invoice status
  goes CONFIRMED → PARTIALLY_PAID → PAID (and RETURNED/CANCELLED untouched); outstanding subtracts a linked non-CANCELLED
  return's credit (check whether the S2 fixture already has a return linked to an invoice; if not, add one — extend the
  fixture generator and keep its drift test and S2's hand-computed numbers consistent).
- **pay / refund:** validation, number kind `PV`, refund flags, supplier purchase-allocation guards.
- **reverse:** unknown id; second reverse refused; entry pair nets to zero; allocations retained but invoices' paid/outstanding
  and status recomputed without them; balances back to pre-payment; audit row; reason required.
- **editAmount:** succeeds on a plain shop voucher and a plain supplier voucher (ledger balance moves by exactly the delta);
  each refusal (reversed / IN voucher / allocated / REFUND-tied by FK / REFUND-tied by heuristic only) with its exact message;
  same-amount and ≤ 0 refused; multiple edits in a row keep exactly one entry.
- **permissions (per operation, per role):** OWNER/MANAGER/ACCOUNTANT allowed as specified, SALES can `receive` but gets 403 on
  `pay`/`refund`/`reverse`/`editAmount`, INVENTORY 403 on everything incl. reads, unauthenticated 401, missing CSRF header
  rejected on POSTs.
- **numbering & concurrency:** parallel receives; two concurrent reverses of one voucher → exactly one succeeds; two concurrent
  receipts racing for one invoice can't over-allocate; idempotency-key replay returns the same voucher and one journal entry.
- **dates:** Karachi-midnight clock test; invalid calendar date rejected.
- **ledger bridge (the important one):** import the synthetic fixture, run a scripted sequence of service operations
  (receive with auto and explicit allocation, pay, refund, reverse, two edits), and apply **the same operations to the
  fixture's legacy-shaped JSON by hand** (the way the legacy code would write those documents); then compare `LegacyLedger`
  balances with the journal-based balances for **every party**, and trial balance = 0. Also re-run importer + reconciliation on
  the fixture and on the real backup (`data/business-20260922-210002-v505-6a81.json`) after your changes: still **0
  differences** (409 customers, 35 suppliers).
- **defence in depth:** a payment inserted directly through the repository with unbalanced lines is rejected by the S1 trigger.
