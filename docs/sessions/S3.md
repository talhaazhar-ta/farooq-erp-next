# S3 — Payments service + API

## Goal

Port the legacy Payments business logic — receive / pay / refund / reverse / editAmount — into a server-side
`PaymentsService` with every guard enforced in NestJS (not just hidden in the UI), each operation posting a
balanced journal entry and an audit row. This is the "business rules and permissions checked only in the
browser" problem the rebuild exists to fix — read `CLAUDE.md` rule 7 before starting.

**Prerequisite:** S1 and S2 done (`docs/STATUS.md` should confirm both; schema and importer exist and are
green). If either isn't done, stop and say so.

## Scope

### 1. Source of truth

Port `D:\projectFarooqAndCoTraders\public_html\ERP\erp-upgrade\02-services.js` around the Payments service
(the old project's `CLAUDE.md` cites roughly lines 1257–1442 as of 2026-09 — re-locate the actual functions,
the file may have moved). Also read the old project's `CLAUDE.md` section "Correcting a paid-out voucher
amount" (2026-09-23) for the `editAmount` refusal rules — this was added recently and its exact refusal
conditions matter:
- refused for a reversed voucher
- refused for a voucher with allocations (e.g. a supplier voucher tied to a purchase)
- refused for the cash side of a customer return's REFUND treatment (that amount is duplicated onto
  `customerReturns.creditAmount` and the two must stay equal)

Port these as literal, testable refusal conditions — don't approximate.

### 2. `PaymentsService` (NestJS, in `apps/api`)

Each operation runs inside one DB transaction:

- **receive** (money in from a shop): amount > 0; shop required (money screens never pre-select a party —
  same rule as the old UI, but enforce it server-side here as "no party = reject", not just a UI default);
  oldest-first `autoAllocate` or explicit allocations; never allocate more than is outstanding.
- **pay** (money out to a supplier): equivalent shape to receive, supplier side.
- **refund** (money paid out to a shop, e.g. against a customer return).
- **reverse**: never deletes a voucher — posts a reversing entry and marks status REVERSED.
- **editAmount**: corrects a voucher's amount in place (no cancel-and-redo), refused per the three conditions
  in §1.

Each operation:
- Posts a balanced `journal_entries`/`journal_lines` row (the S1 trigger should reject it if it's wrong —
  that's the safety net, not a substitute for correct code).
- Writes an `audit_log` row (actor, action, before/after).
- Allocates a receipt number via the `sequences` mechanism from S1, locked with `SELECT … FOR UPDATE`.

### 3. Permission guards

- `PAYMENT_CREATE` gates receive/pay/refund. `TRANSACTION_CORRECT` gates reverse/editAmount. Use the
  permission constants from `packages/shared` (S1) — never a locally re-typed string.
- The old project's open item #7 notes `PAYMENT_CREATE` doesn't currently gate pay-out panels in the live app
  (a known gap). **Here, gate it properly** — this rebuild is the fix, not a faithful reproduction of that gap.
- A guard denial returns 403, and there is a test asserting a role without the permission gets 403 for each
  operation.

### 4. API surface

REST or a typed RPC layer (your call — Nest supports both; if you pick something other than plain REST
controllers, explain why in STATUS) exposing: receive, pay, refund, reverse, editAmount, list/search (basic —
S4 builds the real search UX on top), and a shop/supplier balance read (backed by the same ledger logic S2's
`LegacyLedgerService` reconciles against, but this time the *real* `journal_entries`-based balance, not the
reconciliation-only legacy recompute).

### 5. Tests

One test per legacy rule, not just one test per endpoint. At minimum:
- receive/pay: rejects amount <= 0, rejects missing party, allocates oldest-first correctly, rejects over-
  allocation.
- reverse: original voucher untouched except status; reversing entry balances; reversing an already-reversed
  voucher is rejected (or is a no-op — decide and test it either way).
- editAmount: succeeds on a plain voucher; rejected on a reversed voucher; rejected on an allocated voucher;
  rejected on a REFUND-tied customer-return voucher; each with its own test.
- Every operation: a role without the required permission gets 403.
- A deliberately malformed journal (if you can construct one bypassing the service, e.g. a direct repository
  call in a test) is caught by the S1 trigger, confirming defense-in-depth.
