## Goal

Build the screens on top of S3's write API and S4's read API: the Payments screen (search, filters, list), the five actions
(Receive, Pay supplier, Pay a shop, Reverse, Edit amount), the printable receipt/voucher, and the party statement. Prove it with
Playwright end-to-end tests in headless Chrome, screenshots you actually look at, and a plain "not seen by a person" list.
This closes Milestone 1.

**Prerequisite:** S1–S4 done. Read `docs/STATUS.md` (endpoint tables, the decisions, the Zod schema names), `CLAUDE.md`
(local-preview pattern), `apps/web/src/` (currently: sign-in, shell, dashboard — ~50 lines of router).

## Legacy behaviour to reproduce (read the code)

`38-payment-search.js` (screen layout, filters, "Search in", period presets, problems banner, CSV button, 100-row paging),
`06-wiring.js` (Receive / Pay supplier / Pay a shop / Edit amount panels — search `PANELS.`, `data-fcpayopen`), `04-documents.js`

## Scope

### 1. Foundations
- Introduce the component primitives this session needs the way S1 said it would (dialog, select/combobox, tabs, table, toast). shadcn/ui via
  its CLI is fine (Radix-backed, copies source into `apps/web`); otherwise keep the hand-rolled Tailwind v4 tokens. Either way: keyboard
  accessible, focus-trapped dialogs, visible focus rings, labels tied to inputs.
- Router: real routes (TanStack, code-based is fine): `/payments`, `/payments/:id` (detail + actions), `/payments/:id/receipt` (print
  layout), `/statements` (search params `type=customer|supplier&partyId&from&to`, so a "View statement" link from a row works),
  `/` dashboard stays. State that matters (filters, page, sort, selected party) lives in the **URL search params** — reload and back/forward
  keep the screen (the legacy module 43 behaviour, for free). Nav: enable Payments + Statements; hide entries the role's permissions don't allow
  (`roleHasAnyPermission` from `@farooq/shared`); the other nav entries become visibly disabled ("Soon"), not dead links. A direct URL to a screen
  the role cannot use shows a "Not available for the <role> role" panel (legacy wording style), never a blank page or a raw 403.
- API client: keep `lib/api.ts`; add typed helpers that parse responses with the shared Zod schemas; a 422 `{message, errors}` is shown **verbatim**
  (all `errors`, not just the first, for allocation problems); 401 → back to sign-in; 403 → the not-available panel; network failure → a retry message.
- Money/date at the edge: rupees ↔ paisa only via `@farooq/shared` `parseRupees`/`formatPaisa`; "today" only via `businessDateOf`; dates as native
  `<input type="date">` values (`YYYY-MM-DD`), never through `Date` arithmetic that could shift a day. Urdu digits typed into an amount box are accepted (as in dates).

### 2. Payments screen (`/payments`)
- Search box + "Search in" scope, direction tabs with counts from `facets` (All / Received from shops / Paid to shops / Paid to suppliers / Reversed),
  method, region, period presets (Today, Yesterday, This week, This month, Last month, Last 30 days, Last 3 months, This year, Last 12 months, Custom) computed from
  the business date, amount from–to, sort. The line under the box says how the query was read (`interpreted.dates`, and `problems` in a warning style — legacy behaviour).
  Debounce typing (~250 ms), cancel stale requests, show a loading state that doesn't blank the table.
- Table: receipt no., date, party (Urdu-safe), type, method, reference, amount (right-aligned, tabular figures), applied-to summary / "On account", status badge (Reversed
  rows visually struck), row actions gated by role and by the detail's `actions.*` (a refused action is shown disabled **with the server's reason**, e.g. edit-amount on an allocated voucher).
  Paging 50 per page with total count; **Export CSV** button (the S4 endpoint, same filters).
- Empty and error states are real screens ("No payments match — clear filters"), not a blank table.
- Responsive: usable at 390 px wide (cards or a horizontally scrollable table with the key columns pinned — your call, but no page-level horizontal scroll) and at 1280 px.

### 3. The five actions (panels/dialogs)
- **Receive payment** (`PAYMENT_CREATE`): shop picker (async search combobox over `GET /customers?q=`, starts on "— Choose a shop —", Urdu-safe, shows the balance once chosen),
  date (default today), amount, method (Cash / Bank Transfer / JazzCash — plus what the legacy panel offers), reference, note. After the shop is chosen load
  `outstanding-invoices`: show them oldest first with a **live preview of the automatic oldest-first allocation** (same rule as the server, computed client-side for display
  only) and let the user switch to manual allocation with per-invoice amount boxes capped at each outstanding and a running "left over → on account" line. The server stays the judge:
  show its 422 errors verbatim. **Save is disabled until a party and a valid amount exist**; while saving the button is disabled (double-click safe) and an `idempotencyKey`
  (`crypto.randomUUID()` created when the panel opens, renewed after success) is sent. On success: toast + straight to the receipt view; list and balances refresh.
- **Pay supplier** and **Pay a shop (refund)** (`PAYMENT_PAYOUT`): same shape without allocation preview (supplier: optional purchase allocation if S4/S3 UX warrants — default off). A shop refund
  shows the shop's current balance and, before saving, a plain confirmation line with the balance it will leave ("Shop will owe us Rs …"); it never blocks on balance (the legacy doesn't).
- **Reverse** (`TRANSACTION_CORRECT`): dialog states exactly what will happen (statement/balance effect, allocations released), requires a reason, confirm button says "Reverse voucher".
- **Edit amount** (`TRANSACTION_CORRECT`): dialog shows current amount, new amount (strict parse), reason; when the detail says not allowed, show the reason instead of a form.
- Role behaviour (assert in e2e): OWNER/MANAGER/ACCOUNTANT everything per the permission matrix; SALES sees Receive but no pay-out/reverse/edit; INVENTORY has no Payments/Statements nav and gets the not-available panel on a direct URL.

### 4. Receipt / voucher print (`/payments/:id/receipt`)
Render S4's receipt model: company header (name, taglines, address, phones, logo text), title (PAYMENT RECEIPT / PAYMENT VOUCHER), party block, meta, allocation table, amount,
amount in words, previous/remaining balance, notes, "Received by" and signature lines, and a large REVERSED mark when cancelled. **Print CSS** (`@media print`): A5 or A4 (pick, say which),
shell chrome hidden, **fixed paper colours regardless of theme** (legacy rule), no page-level overflow, fits one page for typical vouchers; "Print" button = `window.print()`. Also a "View statement" link.
No emoji. Both English and Urdu labels where the legacy had them (`وصول رقم`, `بقایا رقم`) — make sure an Urdu-capable font is used in print and screen (system stack with `Noto Naskh Arabic`/`Segoe UI`/`Tahoma` fallbacks;
**do not load external web fonts** — no third-party requests from an ERP page).

### 5. Statement screen (`/statements`)
Filter bar as the legacy (party type toggle, region (customers), party combobox, from/to with presets, "Clear"), opening balance line, rows (date, ref, description, debit, credit, running balance),
totals and closing balance, `omittedReversed` note ("n reversed vouchers are not shown"), **print layout** (repeat the table header per page; fixed paper colours) and CSV/copy if cheap. Balance sign is explained in
words ("Shop owes us" / "We owe supplier", with Cr when the sign flips), never a bare negative number.

### 6. Tests
- **Unit/component (Vitest + Testing Library in `apps/web`; the workspace `test` script must stop being a placeholder):** allocation-preview logic (property test: never over-allocates, matches the
  S3 rule incl. tie-break), amount box parsing/formatting, URL-state ↔ filter mapping, permission-based visibility, the 422 error renderer, the "never pre-selected" rule.
- **Playwright e2e in CI** (`pnpm e2e`; CI installs Chromium; setup: throwaway Postgres → migrate → seed test users for each role with **generated** passwords passed by env (nothing committed) → import the
  synthetic fixture (+ the S4 ~300-payment set for paging/search) → start built api + `vite preview`). Cover: sign-in per role and nav differences; Payments list counts/facets/paging/sort;
  search (multi-word AND, Urdu variant, typed day-first date + the "read as …" line, scopes, amount range, direction tab); Receive with auto-allocation (preview equals the server's result, receipt number
  `REC-<year>-…`, balance on the statement drops by the amount) and with manual allocation (cap enforced in the UI; server refusal shown verbatim via an API-level attempt); Save disabled without a party;
  double-click Save → exactly one voucher; Pay supplier; Pay a shop; Reverse (reason required; balance restored; statement no longer shows it; second reverse impossible in the UI);
  Edit amount (works on a plain voucher; refusal reasons shown for reversed / allocated / return-refund vouchers); CSV export downloads with BOM and correct rows; receipt page → `page.pdf()` contains receipt number,
  amount and amount in words and is **one page**; statement totals equal S4's API; INVENTORY blocked; no page-level horizontal scroll at 390 px; no console errors on the golden paths.
- **Screenshots** of every screen at desktop + 390 px + dark theme, saved under a gitignored `e2e-artifacts/`, **actually looked at** (read them) — record what you saw and any defects fixed.
- Re-run importer + reconciliation on the fixture and the newest real nightly: 0 differences; record numbers.
