## Planner decisions after S7 (binding — don't reopen without a reason written into STATUS)
0. **First, a small S7 follow-through (owner decision 2026-09-24):** anyone holding `SALES_CREATE` may **discard a DRAFT invoice** (cancel of a DRAFT needs
   `SALES_CREATE` **or** `TRANSACTION_CORRECT`); cancelling a **posted** invoice still needs `TRANSACTION_CORRECT`. A draft has no stock, journal or money, so
   nothing else changes. Update the guard/`rules.ts`/`actions.cancel` reason logic in `apps/api/src/invoices/`, the shared permission helpers if any, and the
   S7 tests that assumed the old rule (`invoices-permissions`, `invoices-cancel`, `invoices-reads-duplicate` — change them deliberately and say so in STATUS; SALES
   can discard a draft, still cannot cancel a posted invoice). Add a bite test for each side. Do this first, commit it separately, then the rest of S8.
1. **Search columns (migration `0007`, never edit `0004`–`0006`):** follow S4 — **generated stored columns**, no triggers: on `invoices` `search_customer`
   (shop / customer name / mobile + compact / region snapshots), `search_amount`, `search_date`, `search_other` (notes, description, salesperson, payment method,
   warehouse snapshot, status label words); on `invoice_items` a `search_text` (description / brand / category snapshots). What cannot be a stored column stays a
   query: the shop's **current** text (name, owner, Urdu name, phone, WhatsApp, code, region — join `customers.search_text`) and the receipts applied (number, reference,
   method from `payments` via `payment_allocations`, POSTED only). Product words are an `EXISTS` over `invoice_items`. The legacy rule stays: **receipt numbers are found only with
   the "Receipt / payment ref." scope, never in Everything** (Everything sees the cheque/transaction *reference* only).
2. **List rules:** KPI cards over the filtered list **excluding DRAFT and CANCELLED**, drafts count from *all* invoices (legacy); `due` sort = outstanding desc with drafts/
   cancelled last, ties newest first; source is `invoices` + allocations (never the journal). Status filter uses the eight legacy strings. `paidP` / `outstandingP` come from the
   same functions the detail uses (`apps/api/src/payments/outstanding.ts` and the S7 read model) — one definition.
3. **Profit definition (owner-visible; document both numbers, adopt one):** the legacy `Profit.invoice` counts freight/loading/other charges and tax as profit and ignores the
   invoice-level discount, while `Profit.report` sums line revenue only. **Adopt: invoice profit = Σ over lines (`lineTotal − cost_snapshot × qty`) − invoice discount** —
   goods margin net of the discount actually given; charges and tax are excluded. A line with an unknown cost (`cost_snapshot_p` 0/NULL) is flagged `costKnown: false` and
   excluded from the margin % (its profit is not shown as if the cost were zero). Return both the adopted figure and the legacy `Profit.invoice` figure in a
   `legacyProfitP` field **for the fixture and real-backup comparison test only** (test asserts the two definitions on hand-computed invoices; the field is not part of the public response).
   Only `PROFIT_VIEW` sees any of it; a response for other roles must not contain the keys at all (test the JSON, not just the status).
4. **Print model:** build **classic first** (the live `invoiceTemplate` setting is `classic`; `salesDocPrefix` from `company_profile` → the `SLV-` number = prefix + digits of the invoice number);
   the standard template only if classic is done with all its tests — say in STATUS which was built. The "last 6 ledger rows up to this invoice" come from the S4 statement builder
   (`apps/api/src/statements/`), not a second implementation; the previous balance is the frozen `previous_balance_p`, the "current outstanding balance" is the live journal balance.
   Labels and Urdu strings verbatim from the legacy files (read them; do not re-type). Draft → "DRAFT", no number; cancelled → `cancelled` flag for a stamp. Amount in words via the shared `amountInWords`.
5. **Statement detail (additive only, S5 screens must keep passing untouched):** invoice rows get `description` (typed description, else `N × Name pack @ PKR rate` for one line /
   `N items — X total qty` for several, else `Sale invoice <number>`), `qtyInfo {total, mixed}` and a `qtyLabel`; payment rows show none. Statement CSV/print gain the Qty column only if
   S5's tests stay green with the new field ignored.
6. **CSV:** legacy columns and file name exactly (see Scope), BOM, CRLF quoting as payments' CSV (S4 deviation 7 documents the payments choice — use the same helper), injection guard.

## What S7 actually built (use these names; where this differs from the draft below, THIS wins)

Written by the S7 session. Files: `apps/api/src/invoices/{invoices.service,invoices.controller,invoices.queries,rules,stock,validate}.ts`, shapes in

- **Already existing endpoints (do not rebuild):** `POST /invoices` (`mode: "draft" | "post"`), `PUT /invoices/:id` (edit a draft, post a draft, edit a posted invoice; needs the `revision` the client loaded),
  `POST /invoices/:id/{cancel,duplicate,change-shop}`, `GET /invoices/:id` (the detail: header, `shop` snapshots, `lines`, `receipts`, `stockMovements`, `actions {edit, cancel, changeShop, duplicate}` each
  `{allowed, reason}`), `GET /products?q&warehouseId&limit` (picker: names, brand, `sellP`, `minSellP`, `lastRateP`, `available[]`; `costP` / `buyP` only for `PROFIT_VIEW`), `GET /warehouses`.
  **S8 adds** `GET /invoices` (list), `GET /invoices/export.csv`, `GET /invoices/:id/print` — declare `export.csv` BEFORE `:id` in the controller (as payments do) and reuse `INVOICE_READ_PERMISSIONS`
  (`SALES_CREATE | TRANSACTION_CORRECT | COLLECTION_VIEW | FINANCIAL_REPORT_VIEW`; INVENTORY gets 403).
- **Quantities:** requests use `quantity` (decimal bags, at most 3 decimals); responses give BOTH `quantity` and exact `qtyMilli`. Money is paisa everywhere. `paidP` is derived from POSTED receipts' allocations (not stored);
  `balanceP = total − paid`; `outstandingP` also subtracts non-cancelled customer-return credit. Status strings are the legacy ones (`DRAFT`, `CONFIRMED`, `PARTIALLY_PAID`, `PAID`, `CANCELLED`, `DISPATCHED`, `PARTIALLY_RETURNED`, `RETURNED`).
- **Cancelled invoices** keep their `INVOICE` journal entry and get an `INVOICE_CANCEL` one dated the invoice's date; **statements already omit both** and report `omittedCancelled` (additive to `omittedReversed`). Any S8 search
  KPI (invoiced / received / outstanding) must exclude CANCELLED and DRAFT exactly as the legacy does — the journal is NOT the source for the invoice list (use `invoices` + allocations).
- **Search columns:** `invoices.search_number` exists (S4). Anything else the invoice search needs (customer name, product lines, notes, amount) needs a NEW generated column or a query over `invoice_items` / `customers`
  — add it in a new migration (`0007`); do not edit `0004`–`0006`.
- **Print model inputs already stored:** shop / region / warehouse snapshots on `invoices`, product snapshots and `cost_snapshot_p` on `invoice_items`, frozen `previous_balance_p` (signed), `payment_method`, `reference_no`,
  `notes`, `description`, `salesperson`, `due_date`. Receipts on an invoice: `GET /invoices/:id` → `receipts[]`. The company block comes from `company_profile` as for receipts (S4).
- **Profit:** `cost_snapshot_p` is `costOf` at the time of the last save (re-taken on every edit, like the legacy); 0 = unknown. `avgCostP` is never maintained until M4 — profit uses the snapshot, as the legacy did.
- **Invoice ↔ stock** for search hits ("Paid by REC…", matching product lines) can read `receiptsOn` / `invoice_items` directly.
- **Idempotency:** `request_keys` (kind `INVOICE`) — reads never touch it.

## Scope
- **`GET /invoices`** on the S4 engine (`fold_search`, generated search columns, `parseSearchQuery`): filters status / region / warehouse /
  period / amount (on grand total); sorts newest/oldest/high/low/due; `interpreted`, `problems`, KPI totals (count excl. drafts/cancelled,
  drafts count, invoiced, received, outstanding) and per-status counts; row `hits` (matching product lines "name × qty", receipts "Paid by REC…").
  **Parity:** a literal JS reference of legacy `build` + `matcher` + sorts over legacy-shaped JSON; same ids, same order, same totals on the
  fixture, a seeded ~300-invoice synthetic backup with lines, and the real backup.
- **`GET /invoices/export.csv`** — legacy columns (Invoice, Date, Shop, Owner, Region, Warehouse, Items, Bags, Subtotal, Discount, Charges, Grand total,
  Paid, Balance, Status), BOM, injection guard, file name `farooq-co-invoices-<date>.csv`.
- **`GET /invoices/:id/print?template=classic|standard`** — the document model (company block from `company_profile`, bill-to snapshots,
  lines, totals rows only when non-zero, grand total / amount paid / balance on this invoice with Urdu labels, amount in words, payments against
  it, previous balance (frozen) and current outstanding, signature labels, footer/terms). Classic: `SLV-` digits, last 6 ledger rows up to this
  invoice. Draft → "DRAFT" and no number; cancelled → stamped.
- **Profit** (`PROFIT_VIEW` only; 403 otherwise, never leaked in other responses): per line and per invoice from `cost_snapshot_p`.
- **Statement detail:** invoice rows get the legacy description (typed description, else one-line "200 × Name pack @ PKR 2,700" / "N items — X total
  qty") and a Qty column; update S4's statement response additively; S5 screens keep working.
- `outstanding-invoices` rows gain a line summary (for the Receive panel).
