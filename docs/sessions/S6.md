# S6 — M2 part 1: invoice lines + stock quantities (data model, import, reconciliation)

_Written by the planning hub on 2026-09-24 from the legacy invoice code, the new repo's state after M1, and the newest real nightly
backup. M2 = Invoices; the milestone plan and the owner's decisions are in `docs/ROADMAP.md` → M2. No UI, no invoice writes in S6._

## Goal

Make the database able to hold a sales invoice **as the legacy app has it** — header, lines, and the stock it moved — and prove, like S2
did for balances, that the import is exact:
1. every invoice's total **recomputed from its lines** with a shared port of the legacy `Calc` equals its stored `grandTotal`;
2. every product × warehouse stock quantity equals the legacy `inventory.qty` **and** the sum of its stock movements;
3. shop / supplier balances still reconcile with **0 differences**.

S7 builds the invoice service on this; S8 search/print/profit; S9 the screens.

**Prerequisite:** M1 done (it is). Run `pnpm install && pnpm build && pnpm test` first — expect 541 green (+ `pnpm e2e` 70).
Read `docs/STATUS.md`, `docs/ROADMAP.md` (M2 section: owner decisions), `packages/db/src/schema.ts`, `packages/db/src/ledger.ts`,
`packages/import/src/{classification,prepare,load,reconcile}.ts`, `packages/import/fixtures/build-fixture.ts`.

## Scope

### 1. `packages/shared`: `invoice-totals.ts` (literal port of `Calc`)
Pure functions over paisa and quantities: `lineTotals({qty, unitPriceP, discountP, taxP|taxRate})` and `invoiceTotals({lines, invoiceDiscountP,
freightP, loadingP, otherChargesP, paidP})` → `{subtotal, itemDiscounts, invoiceDiscount, itemTax, grandTotal, balance, paymentStatus, totalQty,
lineCount}` exactly as the legacy: `gross = round(unit × qty)`, line discount capped at gross, invoice discount capped at
`max(0, subtotal − itemDiscounts)`, `qty` rounded to 3 decimals, no whole-invoice rounding, `paymentStatus` = UNPAID when grand ≤ 0 (legacy).
Quantities: represent as **integer thousandths** (`qtyMilli`) inside the function so `round3` is exact; say so. Table tests ported from
`test-erp.mjs` plus property tests (never negative for valid inputs, discount caps hold). This one function is used by the importer's check,
S7's service and S9's live preview.

  `warehouse_snapshot`). `paidAmount` / `balanceAmount` / `paymentStatus` stay **derived** (not stored), as S2 decided.
  **Unique partial index on `invoice_number` WHERE `invoice_number IS NOT NULL`** — drafts carry NULL, so any number of drafts can exist
  (fixes the legacy one-draft bug; test it).
- **`invoice_items`**: `id`, `legacy_id` unique, `invoice_id` FK, `sort_order`, `product_id` FK, `warehouse_id` FK, `description_snapshot`,

- **`stock_movements`** (append-only, like `audit_log`: REVOKE UPDATE/DELETE from the app role in the migration): `id`, `legacy_id` unique,
  `date` (business date), `created_at`, `product_id`, `warehouse_id`, `kind` (text; the legacy kinds), `bucket` (`stock` | the damaged bucket

- **`stock_levels`** (product × warehouse × bucket → `qty_milli`): the current quantity, kept **in the same transaction** as every movement
  (S7's writers); S6 loads it from the legacy `inventory` rows. Also `avg_cost_p`, `last_cost_p` carried verbatim from `inventory` (read by

- **`products` — add** the catalogue fields the invoice builder needs: `name_ur`, `name_en`, `brand`, `brand_en`, `weight_kg` numeric,

  `tax_pct`, `reorder`, all nullable. Mapping: `sellP` if present, else legacy `sell` (rupees → paisa via the strict parser), etc. — mirror
  `Prices.of` exactly and test both sources.
- **Accounts:** none new. The sale entry stays DR RECEIVABLES / CR SALES (no COGS/inventory journal until M4 — record in STATUS).

### 4. Importer
- **Classification changes** (`classification.ts`): `invoiceItems`, `inventory`, `stockMovements` → **imported**. `stockDocs` / `stockDocItems`
  stay **deferred** (their stock effect is already inside `stockMovements`; the documents themselves are M4) — say so in the reason.
  Invoice header fields move from `docOnly` to `mapped` as per §2. Product fields: map the new catalogue/price columns; **pre-classify the
  Prices-panel fields that do not exist in the data yet** (`buyP`, `sellP`, `extraP`, `minSellP`, `wholesaleP`, `retailP`, `discountPct`,
  `taxPct`, `reorder`) as `mapped`, so the first time the owner sets a price the importer keeps working (and a fixture product carries them).
- **Map** invoiceItems (stable deterministic ids as S2; qty → milli exactly — refuse a quantity with more than 3 decimals; money must be
  integer paisa), inventory → `stock_levels` (+ `damagedQty` → the damaged bucket), stockMovements → `stock_movements` (link `source_*` from
  `ref`/`refType`: `INVOICE`/`INVOICE_EDIT`/`INVOICE_CANCEL` → the invoice by number; purchases likewise; unknown refType aborts).
  Fail loudly on: an item whose invoice/product/warehouse doesn't resolve; a movement whose product/warehouse doesn't resolve; an unknown
  `kind`/`bucket`/`refType`; a line on an invoice that is not in the backup.
- **Migrated invoices** (`migrated: true`, `stockApplied: true`, no SALE_OUT movements — none in the real data, but the code creates them):
  import as-is and record them in a report line; S7 must not "reverse" stock that was never taken (put a fixture case in).

### 5. Reconciliation additions (same report, same non-zero exit on any mismatch)
- **Invoice totals:** for every non-DRAFT invoice with lines, `invoiceTotals(lines, charges)` = stored `grandTotal`, and the stored header
  sub-totals (`subtotal`, `discountAmount`, `taxAmount`, `totalQty`, `lineCount`) match; list mismatches by invoice number. Invoices with no lines
  (possible for migrated ones) are listed, not failed.
- **Stock:** for every product × warehouse × bucket: legacy `inventory` qty (and `damagedQty`) = `stock_levels` = Σ `stock_movements`. Also
  informational: rows where the legacy `balanceAfter` chain has gaps.
- **Invoice ↔ stock:** for every posted, `stockApplied`, non-migrated invoice: Σ its SALE_OUT (+ edit reversals) per product equals −Σ its line
  quantities (legacy full-reverse-and-re-deduct edits must net out — prove it on the real data, which has 3 `INVOICE_EDIT` reversals).
- Balances: unchanged, still 0 differences.
- Print real numbers (invoices checked, lines, products × warehouses, movements, quantities in bags), not just "OK".
