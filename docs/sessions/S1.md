# S1 — Scaffold + DB + auth

## Goal

Stand up the pnpm workspace, the NestJS API, the React web shell, the shared permissions/schema package, the
Drizzle Postgres schema with a balance-enforcing trigger, an embedded-Postgres test harness, session/CSRF/role
auth, an owner seed user, and CI. This is the foundation everything else in M1 builds on. **No business
screens yet** — sign-in and an empty authenticated shell is the whole UI surface.

Read `CLAUDE.md` in this repo root first (rules, hard constraints — especially: never deploy, never touch the
live ERP/DB, money is integer paisa, dates are local).

## Scope

### 1. Workspace

- `pnpm-workspace.yaml` covering `apps/*` and `packages/*`.
- `apps/api` — NestJS 11, Fastify adapter (not Express). TypeScript strict mode.
- `apps/web` — React 19 + Vite, TanStack Router + TanStack Query + TanStack Table, shadcn/ui + Tailwind CSS.
- `packages/shared` — Zod schemas, TS types, and the permission-name constants (see §3), importable from both
  `apps/api` and `apps/web`.
- `packages/import` — create the package with just a `package.json` and empty `src/` for now; S2 fills it in.
- Root `package.json` with workspace scripts (`dev`, `build`, `test`, `lint`, `typecheck`) that fan out to each
  package.

### 2. Database (Drizzle + Postgres)

Design a relational, double-entry schema in `apps/api` (or a shared `packages/db` if that separation reads
cleaner once you're in the code — your call, note the choice in STATUS.md):

- `users` (id, legacy_id nullable unique, name, username, password_hash (argon2id), role, active, created_at).
- `sessions` (id, user_id FK, csrf_token, created_at, last_seen_at, expires_at). Cookie is httpOnly, secure in
  prod, SameSite=Lax. Absolute session lifetime and idle handling: read the old project's `CLAUDE.md` §
  "Authentication gate" for the *behaviour* to match conceptually (12h absolute cap, no idle timeout was a
  deliberate owner request) — don't copy config values blindly, just don't contradict that decision without
  flagging it in STATUS.
- `roles` / `role_permissions` — seed with role names and permission strings copied from the old project's
  `erp-upgrade/19-collection-rbac.js` (read that file at `D:\projectFarooqAndCoTraders\public_html\ERP\
  erp-upgrade\19-collection-rbac.js` for the exact role names — OWNER, MANAGER, ACCOUNTANT, SALES, etc. — and
  permission strings — `PAYMENT_CREATE`, `TRANSACTION_CORRECT`, `FINANCIAL_REPORT_VIEW`, etc.). Put the
  permission-name constants in `packages/shared` so api and web both import the same strings — never
  duplicate/hand-retype them.
- Master data: `customers` (shops), `suppliers`, `regions`, `products`, `warehouses`. Each has `legacy_id`
  (unique, nullable) to map back to the old app's IDs during import (S2).
- `accounts` (chart of accounts: Cash/Bank, Receivables-by-shop, Payables-by-supplier, Sales, Purchases,
  Returns, Opening balance equity).
- `journal_entries` (id, date, memo, created_by, created_at) + `journal_lines` (entry_id FK, account_id FK,
  party_type, party_id, debit_p bigint, credit_p bigint). **Add a deferred constraint trigger** that raises if
  a `journal_entries` row's lines don't sum debit==credit at end of transaction. Write a test that inserting an
  unbalanced entry inside a transaction fails at commit.
- `audit_log` (append-only: actor, action, entity, entity_id, before, after, at). The DB role the app connects
  as must have no UPDATE/DELETE grant on this table — enforce with a migration-time `REVOKE`.
- `sequences` table for receipt numbers, incremented under `SELECT … FOR UPDATE` (not a Postgres SEQUENCE
  object, since numbers need to be gap-meaningful the way the old app's receipt numbers are — check the old
  app's receipt-numbering behaviour before deciding; note your finding in STATUS).
- Drizzle migrations checked in under `apps/api` (or wherever you put the db package). Migrations must run
  cleanly against a fresh embedded-postgres instance.
- Invoices/purchases/returns tables: **create them now with header-only columns** (id, legacy_id, party,
  date, total_p, status) since S2's reconciliation needs somewhere to import totals into, but no line-item
  detail yet — that's M2/M3. Keep them intentionally minimal; note in STATUS what's deferred.

### 3. Auth

- Argon2id password hashing (`argon2` npm package or equivalent).
- Login endpoint: username + password → session row + httpOnly cookie + CSRF token (double-submit or header
  pattern — your call, document which).
- A NestJS guard that requires a valid session on protected routes, and a permission guard that checks the
  caller's role against `packages/shared` permission constants (deny by default — a route with no explicit
  permission requirement should not exist for anything beyond health checks).
- Owner seed: a script/migration that creates one `OWNER` user from env vars (never hardcode a password).
- Lockout behaviour: read the old project's known-limits note (5 wrong passwords locks 15 min from any IP) —
  decide whether to port that exactly or improve it (e.g. per-IP instead of per-account-only), and say which
  you chose and why in STATUS. Either is acceptable for S1; don't leave it unspecified.

### 4. Web shell

- Sign-in page (real form, not just fetch-only — should work with JS but also degrade sanely; match the old
  app's decision to make sign-in a real POST where reasonable).
- Authenticated shell: top bar (user chip, sign-out), sidebar nav (can be a stub list of future sections),
  light/dark theme tokens. Doesn't need to visually match the old app pixel-for-pixel, but should not look
  like an unstyled scaffold — this is what "the app exists" looks like to anyone who opens it.
- No business screens/data yet.

### 5. Test harness + CI

- `embedded-postgres` npm package for local dev/test Postgres (no Docker requirement on this machine). Add
  `docker-compose.yml` at repo root for a future VPS, but tests must not depend on Docker being installed.
- Vitest (or Jest — pick one, standard NestJS testing patterns are fine) unit/integration tests for: the
  balance trigger, the permission guard (denies a role without the permission), login success/failure/lockout.
- `.github/workflows/ci.yml`: install, lint, typecheck, unit tests, against a Postgres service container (CI
  can use real Docker-based Postgres even though local dev uses embedded-postgres — that's fine, they don't
  need to match).

## Steps (suggested order, adjust as needed)

1. Scaffold the pnpm workspace and empty packages/apps; get `pnpm install` green.
2. `packages/shared`: permission constants + Zod schemas for users/sessions (enough to unblock api).
3. `apps/api`: Drizzle schema + migrations + the balance trigger; a test proving the trigger works against
   embedded-postgres.
4. `apps/api`: auth (users, sessions, login endpoint, guards); owner seed.
5. `apps/web`: Vite + shadcn/ui setup, sign-in page wired to the real login endpoint, authenticated shell.
6. CI workflow; make sure it's green on a pushed commit before calling this done.
7. Manual check: sign in through headless Chrome (or the `run` skill / CDP approach — see this repo's
   `CLAUDE.md`; there's no established local-preview pattern yet in this project, so set one up and note it in
   STATUS for future sessions to reuse) and confirm the authenticated shell renders.

## Definition of done

- `pnpm install && pnpm build && pnpm test && pnpm typecheck && pnpm lint` all succeed from repo root.
- CI is green on the pushed commit (link/describe the run in STATUS).
- A fresh embedded-postgres instance, migrated from empty, ends with the owner seed user present and the
  balance trigger active.
- A test inserting an unbalanced `journal_entries`/`journal_lines` pair fails at commit — paste the
  test name and result into STATUS.
- Signing in through a real browser (headless Chrome) reaches the authenticated shell with the owner
  credentials — say plainly if this step was skipped and why.
- `docs/STATUS.md` updated with: what's done, the exact verification commands + their output/numbers,
  any deviation from this plan and why, known issues, and "next: S2".
- Nothing uncommitted; pushed to `origin main`.

## Out of scope (leave for later sessions)

- Importer, reconciliation (S2). Payments logic (S3). Payments UI (S4).
- Any business screen beyond the empty authenticated shell.
- Any deployment, hosting decision, or real business data.
- Pixel-perfect visual parity with the old app.
