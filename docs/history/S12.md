# S12 — M3 part 2: Purchases service + API

**Date:** 2026-09-25. **Plan:** `docs/sessions/S12.md` (final; "Planner decisions after S11" followed, none reopened). Service + API only — no screen, no migration.

## What was built

- **`apps/api/src/purchases/`**
  - `purchases.service.ts` — `save(input, actor, id | null)`: create (POST) and edit (PUT) of a purchase in ONE transaction. Lock order **purchase → supplier(s) → stock levels (product, then godown) → numbers**; then, in order: permission and revision checks; validation (`validate.ts`); the edit's own refusals (`rules.ts`), judged only once the form is valid, like the legacy; cost allocation; header; lines (kept lines keep their id, dropped ones are deleted, the new ones get a fresh id); stock; average cost (`cost.ts`); the journal; the payout; audit. Idempotency through `request_keys` (kind `PURCHASE`; a key already used by an invoice save is refused). The number is `<purchasePrefix setting, default PUR>-<business year>-<6>` from `nextNumber`.
  - `validate.ts` — `Validate.purchase` (legacy messages verbatim, in order, all collected) plus the owner's new rules (paid below 0 / above the total on a new purchase, a line discount above the line amount, negative discount / charges, more than 3 decimals).
  - `rules.ts` — the legacy `editErrors` as a pure function (returned / landed line cannot be removed or re-producted, received cannot go below returned, supplier lock, paid cannot be lowered, net stock guard) + `netStockChange` + the two supplier-lock sentences.
  - `cost.ts` — `recomputeAverages`: for every product × godown touched now or before the edit, `weightedAverage` over all non-cancelled purchase lines on the `readProfitCostBasis` basis; a number writes `avg_cost_p` (+ `last_cost_p` = the saved line's unit when the pair still has a line); `null` + a saved line in the pair = the legacy fall-back (avg = last = that line's unit); `null` on a pair only dropped = left alone. Sellable bucket only.
  - `purchases.queries.ts` / `purchases.controller.ts` — `GET /purchases/:id` (header, lines, vouchers with allocations, stock movements, `actions.edit {allowed, reason}`; `costs` and the per-line cost columns only with `PROFIT_VIEW`, the keys absent otherwise), `GET /purchases/last-rates?productIds=…`, `POST /purchases` (`PURCHASE_CREATE`), `PUT /purchases/:id` (`PURCHASE_CREATE` or `TRANSACTION_CORRECT`; paying more also needs `PAYMENT_PAYOUT`, else 403 and the whole save is refused). Reads: any of `PURCHASE_CREATE | TRANSACTION_CORRECT | FINANCIAL_REPORT_VIEW` (INVENTORY and SALES 403).
- **`apps/api/src/payments/payout-core.ts`** — `writePayout(tx, actor, today, input)` and `checkPurchaseAllocations` extracted from `PaymentsService.pay` (the way S7 extracted `writeReceipt`); `pay` and a purchase saved with money both call it; S3's tests run unchanged.
- **`apps/api/src/invoices/stock.ts`** — `applyStockMovement` (any document's movement, with a unit cost and a source type); `applyMovement` now delegates to it (invoice behaviour unchanged).
- **`packages/shared/src/schemas/purchases.ts`** — `PURCHASE_MESSAGES`, `savePurchaseSchema` (strict), the detail / rate schemas.
- **Docs:** PARITY "Purchases service — ported in S12" (rule → test table), ROADMAP, CLAUDE.md (test paragraph), S13 / S14 corrections.
- **e2e:** the flaky `invoices-builder.spec.ts` toast reads now find the toast by its text (`filter({ hasText })`) instead of `.first()` (STATUS asked for it).

## Deviations from the plan / decisions

- **Different from the legacy (all in PARITY):** paid > total / negative refused on a new purchase; a line discount above the line amount refused; negative discounts / charges and > 3 decimals refused; the part-delivery cost fixed; **net movements instead of reverse + re-add** (the stock history shows fewer rows; a date-only edit posts none); `costHistory` not kept; an imported DRAFT purchase takes a real status when saved; a purchase key shares `request_keys` with invoices.
- **Edit body is the whole form** (a full PUT): fields left out are cleared, except `description` (kept) and `paidAmountP` (defaults to what is paid). S14's plan says so.
- **`received_qty` above ordered is accepted** (the legacy allowed it); a purchase needs at least one line (an unchanged save of a line-less imported purchase is refused — none exist in the real data).
- **The supplier-return lock** reads `returns.legacy_doc->>'purchaseId'` (matched to the purchase's legacy id) and `purchase_items.returned_qty_milli` until M5 gives returns a column of their own; a test seeds both.
- **The payout gate** and the cost-key visibility are proved by temporarily removing a permission from a role's array in the test process (no built-in role holds `PURCHASE_CREATE` / `TRANSACTION_CORRECT` without `PAYMENT_PAYOUT` / `PROFIT_VIEW`).
- The detail has **no "why can't I change the supplier" field** (found while planning S14): S13 adds `actions.changeSupplier`.
- The purchase number's prefix is read from the imported `purchasePrefix` setting (default `PUR`); invoices / receipts still use fixed prefixes.

## Findings

- A negative rate was also reported as "the discount is larger than the line amount" (gross < 0): found by the unit test, fixed (the comparison needs a valid rate and quantity).
- The legacy deleted a reversed voucher's allocation row; here it stays (S3), so the reconciliation's `paymentAllocations` count differs by one per reversed allocated voucher — listed in the bridge as an expected count difference.
- An edit racing a supplier payment on the same purchase cannot deadlock: both lock the purchase first, then take the PV number.
- Unchanged saves of real purchases are exact — the legacy weighted average, the landed unit and the fix-3 allocation all reproduce the legacy's stored figures on real data.
